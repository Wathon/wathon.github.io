    Building an On-Premises Lakehouse: Lessons from Spark, Iceberg, and Nessie in Banking

    Published Jan 15, 2025 • Technical Deep Dive

    The Regulated Banking Challenge

    In enterprise financial institutions, data platforms must comply with strict auditability, zero-data-loss guarantees, and air-gapped on-premise infrastructure constraints. Traditional Hive metastores and relational warehouses struggle when ETL jobs require non-blocking schema evolution or isolated pipeline staging.

    The Architecture: Decoupled Lakehouse Stack

    To solve this, we architected a modern Lakehouse on Kubernetes combining MinIO (S3-compatible distributed object storage), Apache Iceberg (ACID table format), Project Nessie (transactional Git-like catalog), Apache Spark (batch compute), and Trino (distributed SQL query engine).

    Why the Manual is Wrong: Catalog Branching in Production

    Standard Iceberg documentation suggests writing directly to tables and relying on snapshot rollbacks if an error occurs. In banking, rollbacks on live tables can interrupt active BI dashboards and central bank reporting queries.

    The Nessie Solution: We implemented Git-like branching for our ETL pipelines. The Airflow DAG creates an ephemeral branch (e.g., branch-etl-daily-tx), writes transformations via Spark, executes dbt data quality tests, and performs an atomic merge into the main branch only after all validation checks pass. If tests fail, the branch is dropped with zero impact on production queries.

    Mitigating the Small-File Problem

    Frequent batch writes quickly generated hundreds of thousands of small Parquet files. We automated off-peak Spark compaction jobs using Iceberg's rewrite_data_files action with bin-pack strategies and tuned snapshot retention to 7 days, maintaining sub-second Trino query speeds across multi-terabyte analytical tables.

    Why the Manual is Wrong: Solving Spark Shuffle Spills & Memory OOMs on Kubernetes

    Published Nov 10, 2024 • Production Post-Mortem

    The Failure Mode

    When scaling batch ETL jobs across millions of transactional records, Spark executor pods on Kubernetes were intermittently terminated with Exit Code 137 (OOMKilled). The standard advice in forums is simply to "increase spark.executor.memory", but doing so only delayed the crashes and doubled infrastructure costs.

    Understanding Kubernetes Memory vs. JVM Heaps

    Kubernetes memory limits enforce a hard container ceiling. Spark's memory footprint is not just the JVM heap (spark.executor.memory); it includes Netty network shuffle buffers, off-heap storage, and Python/C extension memory. When shuffle data spills to disk or fills Netty buffers faster than the OS can flush them, the Linux kernel terminates the pod.

    The 3-Step Production Remedy

    1. Off-Heap Headroom: Increased spark.kubernetes.memoryOverheadFactor from the default 0.10 to 0.22, allocating explicit off-heap headroom for network shuffle buffers.
    2. Adaptive Query Execution (AQE): Enabled spark.sql.adaptive.enabled=true and spark.sql.adaptive.coalescePartitions.enabled=true to dynamically combine small post-shuffle partitions and automatically handle skewed join keys.
    3. Broadcast Hints for Dimension Joins: Configured spark.sql.autoBroadcastJoinThreshold=32MB to eliminate expensive network shuffles during account metadata joins.

    Outcome

    Completely eliminated container eviction failures during peak daily batch windows while decreasing overall cluster memory consumption by 30%.

    Designing Idempotent and Resilient ETL Pipelines on AWS Serverless

    Published Jul 22, 2024 • Architecture Blueprint

    The Reality of Distributed Cloud Ingestion

    In serverless event architectures (API Gateway → Lambda → S3 → Glue), network timeouts and upstream client retries inevitably generate duplicate event payloads. Without idempotent pipeline design, duplicated banking transactions can silently corrupt financial aggregates.

    The Idempotency Key Pattern

    We implemented deterministic SHA-256 fingerprint hashing over natural transaction attributes (account_number + timestamp + transaction_type + amount + external_ref). This idempotency hash travels through the entire S3 bronze/silver hierarchy.

    During Redshift warehouse loading, we applied an atomic staging-table merge pattern within a single transaction block:
    BEGIN; DELETE FROM target_table USING staging_table WHERE target_table.idempotency_hash = staging_table.idempotency_hash; INSERT INTO target_table SELECT * FROM staging_table; COMMIT;

    Graceful Failure & Dead-Letter Isolation

    Schema drift and corrupt payloads are intercepted by AWS Lambda schema validators and routed directly to SQS Dead-Letter Queues (DLQ) with automated CloudWatch alerting. This isolates corrupted records immediately, allowing 99.9% of valid transaction traffic to process without blocking downstream reporting.
